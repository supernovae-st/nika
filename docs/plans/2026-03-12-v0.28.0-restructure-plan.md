# Nika v0.28.0 - Architecture Restructure Plan

**Date**: 2026-03-12
**Author**: Claude (Opus) + Thibaut
**Status**: Planning
**Research**: Context7 + rust-pro + 30-agent audit findings

---

## Executive Summary

v0.28.0 focuses on **architecture restructure** to improve maintainability, compile times, and enable external consumers of Nika's core functionality. Based on analysis of 8 major Rust projects (rig-core, mistral.rs, Helix, Zed, nushell) and our 30-agent audit findings.

### Key Metrics
- **Current**: 210K LoC, monolithic crate, ~4 min compile time
- **Target**: 3 crates (minimal split), ~2 min compile time, clean API boundaries
- **Tests**: 6,157 passing (maintain 100% pass rate)

## Phase 2: API Cleanup

### 2.1 Public API Design (nika-core)

```rust
// nika-core/src/lib.rs

// AST types (public)
pub mod ast {
    pub use crate::ast::raw::{parse, RawWorkflow, RawTask};
    pub use crate::ast::analyzed::{AnalyzedWorkflow, AnalyzedTask, TaskId};
    pub use crate::ast::analyzer::{analyze, AnalyzeResult};
}

// DAG types (public)
pub mod dag {
    pub use crate::dag::{Dag, DagNode, DagEdge, validate_dag};
}

// Error types (public)
pub use crate::error::{NikaError, NikaErrorCode, Result};

// Provider/Model definitions (public)
pub use crate::providers::{KNOWN_PROVIDERS, ProviderInfo, ProviderCategory};
pub use crate::models::{KNOWN_MODELS, ModelInfo, ModelFamily};
pub use crate::mcp_aliases::{MCP_ALIASES, McpAliasInfo};
```

### 5.1 Compile Time Targets

|--------|---------|--------|

### 5.2 Optimizations

1. **Workspace-level target sharing** - Single target/ directory
2. **Parallel crate compilation** - Independent crates compile in parallel
3. **sccache integration** - CI cache for dependencies
4. **Feature flag optimization** - Disable unused optional deps

## Alternatives Considered

### Option A: Keep Monolithic (Rejected)
- Pros: No migration effort
- Cons: Growing compile times, no clean API

### Option B: Full Split (7 crates) (Deferred to v0.30)
- Pros: Maximum flexibility
- Cons: Too much migration effort for v0.28

### Option C: Minimal Split (3 crates) (Chosen)
- Pros: Best balance of effort vs benefit
- Cons: TUI still large (~90K LoC)

## Appendix: Research Summary

### From 30-Agent Audit

Key findings that inform this plan:

1. **spn→nika cleanup is 95% complete** - Only naming artifacts remain
2. **Feature flags need consolidation** - Some redundant flags
3. **TUI is largest module** (~90K LoC) - Consider further split in v0.30
4. **Test coverage gaps** - daemon, TUI views need more tests
5. **Error handling inconsistent** - Some errors lack context

### From Context7 Research

- **rig-core patterns** - Stay monolithic at 58K, split after 100K
- **mistral.rs patterns** - Split by capability, not arbitrary modules
- **Helix patterns** - TUI + core separation works well

### From rust-pro Analysis

- **Workspace overhead**: ~5% compile time increase
- **Feature flag cost**: <1% per feature
- **Recommended split threshold**: 100-200K LoC
