## BUG-1: Output polluted by CLI display (CRITICAL — user-facing)

**Symptom:** When a workflow completes via `nika serve`, the job output contains the full CLI display (Performance stats, Timeline Gantt bars, Provider Breakdown table, trace path) instead of just the LLM result text.

**Root cause:** The default executor is `Subprocess`. It spawns `nika run workflow.nika.yaml --no-live -y --no-interactive` and captures stdout. But `--no-live` only disables animation — the summary box still prints to stdout. The subprocess captures ALL of stdout as the job output.

**Why `--quiet` doesn't fix it:** In quiet mode, `nika run` suppresses the summary BUT ALSO suppresses the final output text (`main.rs:2505`: `if !quiet && !run_output.is_empty()`). So with `--quiet`, the subprocess captures nothing useful.

**The embedded executor doesn't have this bug:** `executor.rs:100` calls `.quiet()` on the Runner and gets the clean output from `runner.run()` which returns `Result<String>`.

### Fix

**File:** `tools/nika-serve/src/config.rs`

```rust
// Line 13-18: Move #[default] from Subprocess to Embedded
#[derive(Clone, Debug, Default, PartialEq, Eq)]
pub enum ExecutorMode {
    /// V1: spawn `nika run <workflow>` as a subprocess.
    Subprocess,
    /// V2: run workflow in-process via embedded nika-engine Runner (default).
    #[default]
    Embedded,
}
```

```rust
// Line 94-99: Change fallback from "subprocess" to "embedded"
let executor_mode = match std::env::var("NIKA_SERVE_EXECUTOR")
    .as_deref()
    .unwrap_or("embedded")  // was "subprocess"
{
    "subprocess" => ExecutorMode::Subprocess,
    _ => ExecutorMode::Embedded,
};
```

**Also update test fixtures:**


## BUG-2: Env allowlist leaks secrets to workflows (CRITICAL — security)

**Symptom:** Any environment variable ending in `_KEY` is passed to every workflow subprocess.

**File:** `tools/nika-serve/src/worker.rs:288-297`

```rust
k.ends_with("_API_KEY")
    || k.ends_with("_KEY")      // <-- TOO BROAD
    || k == "RUST_LOG"
    || k == "NIKA_VAULT_PASSPHRASE"  // <-- MASTER DECRYPTION KEY
    || k.starts_with("NIKA_ENDPOINT_")
```

**Problems:**
1. `k.ends_with("_KEY")` matches `DEPLOY_KEY`, `SSH_HOST_KEY`, `GPG_KEY`, etc.
2. `NIKA_VAULT_PASSPHRASE` is the master decryption key for NikaVault. A malicious workflow with `exec: "env | grep VAULT"` can exfiltrate all API keys.

### Fix

Replace the broad suffix match with an explicit allowlist:

```rust
let nika_vars: Vec<(String, String)> = std::env::vars()
    .filter(|(k, _)| {
        // Explicit LLM provider keys only
        k == "ANTHROPIC_API_KEY"
            || k == "OPENAI_API_KEY"
            || k == "XAI_API_KEY"
            || k == "GEMINI_API_KEY"
            || k == "MISTRAL_API_KEY"
            || k == "GROQ_API_KEY"
            || k == "DEEPSEEK_API_KEY"
            // Nika operational vars
            || k == "RUST_LOG"
            || k == "NIKA_NO_DAEMON"
            || k.starts_with("NIKA_ENDPOINT_")
            // NEVER pass NIKA_VAULT_PASSPHRASE to workflows
    })
    .collect();
```

Remove `NIKA_VAULT_PASSPHRASE` entirely — the embedded executor doesn't need it (vault is already unlocked in the parent process), and the subprocess executor should use daemon IPC for secrets.

## BUG-3: Shutdown signal fires too late (CRITICAL — reliability)

**Symptom:** On SIGTERM, workers don't receive the shutdown signal until after Axum has fully stopped. Jobs in the queue or mid-execution keep running during the 30s drain window without knowing they should stop.

**File:** `tools/nika-serve/src/lib.rs:196-207`

```rust
// Axum blocks here until all connections close
axum::serve(listener, app)
    .with_graceful_shutdown(shutdown_signal)
    .await?;

// Only THEN do we signal workers — too late!
let _ = shutdown_tx.send(true);
```

### Fix

Signal workers immediately when the OS signal arrives, not after Axum finishes:

```rust
let shutdown_signal = async move {
    // ... wait for SIGTERM/SIGINT ...
    info!("shutdown signal received, notifying workers");
    let _ = shutdown_tx.send(true);  // Signal workers FIRST
};

axum::serve(listener, app)
    .with_graceful_shutdown(shutdown_signal)
    .await?;

// Workers already notified, just drain
drain_workers(state.workers.clone()).await;
```

This requires moving `shutdown_tx` into the signal closure. It's already `let (shutdown_tx, _) = tokio::sync::watch::channel(false);` — just move the `send` inside the signal future.

## BUG-4: active_jobs counter leak on storage failure (IMPORTANT)

**Symptom:** If `create_job()` fails (SQLite locked, disk full), the `active_jobs` AtomicUsize counter is incremented but never decremented. After enough failures, all new jobs are rejected with "Queue full" even when no jobs are running.

**File:** `tools/nika-serve/src/routes/workflows.rs:90-98`

```rust
try_acquire_job_slot(&state.active_jobs, max_queued)?;  // ← increments
// If this line fails, counter is orphaned:
state.storage.create_job(&job_id, &req.workflow).await?;
```

### Fix

Decrement on error:

```rust
try_acquire_job_slot(&state.active_jobs, max_queued)?;

if let Err(e) = state.storage.create_job(&job_id, &req.workflow).await {
    state.active_jobs.fetch_sub(1, std::sync::atomic::Ordering::Relaxed);
    return Err(e.into());
}
```

## BUG-5: SSE creates orphan channels for non-existent jobs (IMPORTANT)

**Symptom:** `GET /v1/events/{id}` with a fake job_id creates a permanent broadcast channel in the EventBus HashMap. An attacker can exhaust memory by opening thousands of SSE connections with random IDs.

**File:** `tools/nika-serve/src/events.rs:86-90`

```rust
pub async fn stream_events(...) -> Sse<...> {
    let rx = state.event_bus.subscribe(&job_id).await;
    // subscribe() calls sender() which calls or_insert_with() — always creates entry
```

The comment at line 83-84 says "the client may have connected before the job was created" — but this is a risky assumption for a public API.

### Fix

Check job exists in storage before subscribing:

```rust
pub async fn stream_events(...) -> Result<Sse<...>, ServeError> {
    // Verify job exists (or was recently created)
    let job = state.storage.get_job(&job_id).await
        .map_err(|_| ServeError::Internal(...))?
        .ok_or(ServeError::NotFound)?;

    let rx = state.event_bus.subscribe(&job_id).await;
    // ... rest unchanged
}
```

## BUG-6: Input key validation missing (IMPORTANT)

**Symptom:** API callers can send input keys containing `=`, spaces, or shell metacharacters. The key is concatenated into `--input key=value` args. A key like `foo=bar` produces `--input foo=bar=baz` which corrupts the argument protocol.

**File:** `tools/nika-serve/src/worker.rs:275-282`

```rust
cmd.arg("--input").arg(format!("{key}={val_str}"));
```

### Fix

Validate input keys in the route handler before spawning:

```rust
// In routes/workflows.rs, after validating workflow path:
if let Some(inputs) = &req.inputs {
    if let Some(obj) = inputs.as_object() {
        for key in obj.keys() {
            if !key.chars().all(|c| c.is_ascii_alphanumeric() || c == '_') {
                return Err(ServeError::InvalidWorkflow(
                    format!("invalid input key: {key}")
                ));
            }
        }
        if obj.len() > 64 {
            return Err(ServeError::InvalidWorkflow(
                "too many inputs (max 64)".into()
            ));
        }
    }
}
```

## BUG-10: Polling race condition — setInterval fires while previous poll is in-flight (CRITICAL — client-side)

**Symptom:** Dashboard shows 10+ GET /v1/status requests piling up. Job shows "completed" but polling continues. Apparent 20s interval between visible responses (actually 2s ticks with 20s round-trip each).

**Root cause:** `setInterval(tick, 2000)` fires every 2s regardless of whether the previous `$fetch` has resolved. If nika serve takes 20s to respond (long workflow), 10 simultaneous polls accumulate. When the first returns "completed" and calls `stopPolling()`, the other 9 in-flight fetches still resolve and overwrite the job status — potentially reverting "completed" back to "running".

**File:** `test-jungo/pages/index.vue` — the `startPolling()` function

### Fix

Replace `setInterval` with a self-scheduling `setTimeout` chain + abort guard:

```ts
let pollAborted = false;

function startPolling(jobId: string) {
  stopPolling();
  pollErrors = 0;
  pollAborted = false;

  async function tick() {
    if (pollAborted) return;
    try {
      const status = await nika.pollStatus(jobId);
      if (pollAborted) return;
      pollErrors = 0;
      nika.updateJob(jobId, { status: status.status, output: status.output });
      if (['completed', 'failed', 'cancelled'].includes(status.status)) {
        stopPolling();
        stopElapsed();
        isRunning.value = false;
        nika.updateJob(jobId, { elapsed: elapsed.value });
        return;
      }
    } catch {
      if (pollAborted) return;
      pollErrors++;
      if (pollErrors >= 3) {
        stopPolling(); stopElapsed(); isRunning.value = false;
        return;
      }
    }
    pollInterval = setTimeout(tick, 2000) as any;
  }

  tick();
}

function stopPolling() {
  pollAborted = true;
  if (pollInterval) { clearTimeout(pollInterval); pollInterval = null; }
}
```

Key difference: `setTimeout` waits for the PREVIOUS poll to complete before scheduling the next one. No more pile-up.

## BUG-11: `--quiet` mode suppresses final output too — subprocess output is empty (CRITICAL)

**Symptom:** Even if you add `--quiet` to the subprocess args, the output field will be empty. In quiet mode, `main.rs:2505` does `if !quiet && !run_output.is_empty()` — the `println!` that writes the actual result to stdout is skipped.

**Root cause:** `nika run` was designed for human display, not machine consumption. There is no flag that outputs ONLY the LLM result to stdout with zero decoration.

**File:** `tools/nika/src/main.rs:2505-2508`

```rust
// This is the ONLY place the actual LLM result goes to stdout
if !quiet && !run_output.is_empty() {
    println!("{}", "Output:".cyan().bold());

```

With `--quiet`: this block is skipped entirely. Without `--quiet`: the result is printed but mixed with CLI display.

### Fix

**This is why BUG-1 (switch to embedded executor) is the correct fix.** The embedded executor calls `runner.run()` which returns the clean `String` directly — it never touches stdout.

**If subprocess must be supported:** Implement IMPROVEMENT-1 (`--machine-output` flag).

## GAP-1: API returns only final task output — intermediate outputs lost (ARCHITECTURE GAP)

**Context:** Every task in a workflow produces an output. Those are stored in the engine's `Datastore` (in-memory `HashMap<TaskId, TaskResult>`) during execution. But the API only returns ONE string.

**How the "final output" is selected:**

```rust
// nika-engine/src/runtime/runner.rs:539-559
fn get_final_output(&self) -> Option<String> {
    // Returns the output of the DEEPEST terminal task in the DAG
    self.flow_graph.get_deepest_final_task()
}
```

For a workflow like:
```yaml
tasks:
  - id: research      # output → "AI is fascinating because..." (LOST via API)
    infer: "Research AI"
  - id: summarize     # output → "In short, AI transforms..."  (RETURNED via API)
    depends_on: [research]
    with: { data: $research }
    infer: "Summarize: {{with.data}}"
```

GET /v1/status returns ONLY `summarize`'s output. `research`'s output is gone.

**What Nicolas needs for i18n:** The translate workflow produces 200 artifacts (one JSON file per locale). The API returns the output of the LAST task only. Nicolas needs access to ALL outputs or at least the artifacts.

### Where intermediate outputs exist

| Location | Accessible via API? | Contains |
|----------|---------------------|----------|
| `Datastore` (in-memory) | NO — dies after runner.run() returns | All task outputs |
| Trace NDJSON file (`.nika/traces/`) | NO — filesystem only | All events + outputs |
| Artifacts (filesystem) | NO — filesystem only | Files written by `artifact:` blocks |
| `runner.run()` return value | YES — but only 1 string | Deepest terminal task output |
| `-o FILE` flag output | NO — filesystem only | JSON with all task outputs + durations |

### Proposal: Enrich the status response

**Option A (minimal):** Add a `tasks` field to the status response with per-task output:

```json
GET /v1/status/{id}
{
  "status": "completed",
  "output": "In short, AI transforms...",
  "tasks": {
    "research": { "status": "success", "duration_ms": 2100 },
    "summarize": { "status": "success", "duration_ms": 1800 }
  }
}
```

This requires the embedded executor to capture per-task results from the datastore before it's dropped. Modify `executor.rs` to call `runner.datastore().iter_results()` (same API used by `-o FILE` in `main.rs:2477-2503`).

**Option B (full):** Add per-task outputs:

```json
{
  "tasks": {
    "research": { "status": "success", "output": "AI is fascinating...", "duration_ms": 2100 },
    "summarize": { "status": "success", "output": "In short...", "duration_ms": 1800 }
  }
}
```

This exposes all intermediate data but can be huge for large workflows. Gate behind a `?detail=full` query param.

**Option C (artifacts):** Add an artifact listing endpoint:

```
GET /v1/artifacts/{job_id}
→ { "files": ["output/fr-FR/ui.json", "output/ja-JP/ui.json", ...] }

GET /v1/artifacts/{job_id}/{path}
→ raw file content (application/octet-stream)
```

This is what Nicolas actually needs for i18n. The workflow writes artifacts to disk, and this endpoint serves them back. Requires tracking which artifacts a job produced (artifact manifest in SQLite or on disk).

## ROADMAP: nika serve V3 — Production API

> Based on research of 7 workflow engines (Temporal, Windmill, Hatchet, Inngest, Replicate, Vercel AI, GitLab CI).
> Full research reports in `test-jungo/docs/research/2026-04-01-*.md` (4 reports).

### Design Principles (stolen from the best)

1. **Windmill `get_result_maybe` pattern** — one endpoint, never 404, always returns state + result when ready
2. **Hatchet DX** — `await nika.run()` → typed result. 2 lines. Done.
3. **GitLab artifact API** — per-file download via path, not forced ZIP
4. **Vercel AI typed SSE** — `task_start`, `task_complete`, `progress` events
5. **Replicate split URLs** — POST returns `stream_url` for SSE separately from poll URL

Rename `/v1/status/{id}` → `/v1/jobs/{id}` (keep old as alias).

### Target API: Artifact Download

```
GET /v1/jobs/{id}/artifacts
→ { "artifacts": [{ "path": "fr-FR/ui.json", "size": 4096, "mime": "application/json" }, ...] }

GET /v1/jobs/{id}/artifacts/fr-FR/ui.json
→ raw file content (Content-Type: application/json, ETag: <cas-hash>)
```

Path traversal blocked. Files scoped to job. CAS-native with immutable caching.

### Target: Nika SDK — Rust Core, Native Bindings

> Research: `test-jungo/docs/research/2026-04-01-nika-sdk-architecture.md`
>
> The SDK is NOT a thin HTTP wrapper. It's Nika compiled to every platform via native bindings.
> Precedent: SWC (60M downloads/mo), Prisma, Ruff, Polars — all Rust core + native bindings.

#### Architecture

```
nika-sdk-core (Rust crate, ~2000 lines)
    │
    ├── [embedded mode] → nika-engine in-process (zero network, fastest)
    │     Parse YAML, validate DAG, resolve templates, execute — all native
    │
    └── [remote mode] → nika-serve HTTP+SSE (universal, stateless client)
          POST /v1/run → poll /v1/jobs/{id} → download artifacts

Language bindings (auto-generated types, zero JSON serialization overhead):
    ├── napi-rs  → @nika/sdk  (npm, Node.js native addon)
    ├── PyO3     → nika-py    (pip, Python native module)
    ├── wasm     → @nika/wasm (npm, browser/Deno/Bun)
    └── HTTP     → REST       (any language, fallback)
```

#### What Nicolas writes (Node.js)

```js
import { Nika } from '@nika/sdk';  // native Rust binary in node_modules

// Remote mode — talks to nika serve on VPS
const nika = new Nika({ url: 'http://vps:3000', token: process.env.NIKA_TOKEN });

// Simple — 1 line, typed result
const result = await nika.run('translate.nika.yaml', { file: 'ui.json' });
console.log(result.output);     // final task output (clean string)
console.log(result.tasks);      // per-task results { translate[0]: { status, duration_ms }, ... }
console.log(result.artifacts);  // [{ path: "fr-FR/ui.json", size: 4096 }, ...]
console.log(result.cost);       // { total_usd: 0.04, input_tokens: 12000, output_tokens: 8000 }

// With progress — callback fires per-task
const job = await nika.run('translate.nika.yaml', { file: 'ui.json' }, {
  onProgress: (p) => console.log(`${p.percent}% — ${p.current_task}`),
  onArtifact: (a) => console.log(`Ready: ${a.path}`),
});

// Download artifact — zero-copy from CAS
const json = await nika.artifact(job.id, 'fr-FR/ui.json');
fs.writeFileSync('i18n/fr-FR/ui.json', json);

// Stream mode — async iterator over typed SSE events
for await (const event of nika.stream('translate.nika.yaml', { file: 'ui.json' })) {
  if (event.type === 'task_completed') console.log(`${event.task_id} done`);
  if (event.type === 'artifact_written') console.log(`File: ${event.path}`);
  if (event.type === 'progress') console.log(`${event.percent}%`);
  if (event.type === 'workflow_completed') {
    console.log(event.result);
    break;
  }
}

// Embedded mode — Nika engine runs IN Nicolas's process (no VPS needed)
const local = new Nika({ mode: 'embedded' });
const result = await local.run('workflow.nika.yaml', { topic: 'AI' });
// No network, no server, YAML parsed and executed natively in Rust
```

### Workflow-Level `output:` Declaration

Currently the "output" is implicitly the deepest terminal task. Add explicit control:

```yaml
# Implicit (backward compat) — last task output
tasks:
  - id: greet
    infer: "Say hello"

# Explicit single — author chooses which task is "the result"
output: $summarize

# Explicit multi — multiple named outputs
output:
  summary: $summarize
  facts: $research

# Artifacts as output — the files ARE the result
output: artifacts
```

The engine checks for `output:` in the workflow header. If present, uses it. If absent, falls back to `get_deepest_final_task()`. Multiple terminal tasks without `output:` declared → auto-merge into `{ taskA: "...", taskB: "..." }`.

### Architecture Innovations (from research)

> Research: `test-jungo/docs/research/2026-04-01-workflow-engine-architecture-research.md`

#### 1. Content-Addressable LLM Cache (stolen from Dagger)

Same prompt + same model + same temperature = same result. Cache key:

```
BLAKE3(provider + model + temperature + prompt + system + schema)
```

On cache hit: skip the LLM call entirely, return cached result. Saves real money on re-runs and debugging. The CAS already exists in nika-engine — extend it to LLM responses.

```yaml
# In nika.toml:
[cache]
enabled = true
ttl = "7d"
max_size = "1GB"
```

#### 2. Checkpoint Store for Crash Recovery (stolen from Restate/DBOS)

After each task completes, write a checkpoint to SQLite:

```sql
INSERT INTO checkpoints (workflow_run_id, task_id, output, completed_at) VALUES (?, ?, ?, ?);
```

On crash: `nika run --resume <run_id>` reads checkpoints, skips completed tasks, resumes from the first incomplete one. For a 200-locale translation that crashes at locale 150: restart from 151, not from 0.

#### 3. `nika run --from <task_id>` (stolen from DBOS)

Debug a failing task without re-running the entire workflow:

```bash
nika run translate.nika.yaml --from translate[150]
# Loads checkpoints for tasks 0-149, executes from 150 onwards
```

### Performance Architecture

> Research: `test-jungo/docs/research/2026-04-01-streaming-performance-and-storage-patterns.md`

```
Layer          Technology                    Target Latency
─────          ──────────                    ──────────────
Events         tokio::broadcast (per-job)    ~100 microseconds
               + TCP_NODELAY on SSE
SSE delivery   Axum SSE + keep-alive 15s     ~200 microseconds
File serving   mmap LRU cache + ETag         ~200us (hot), ~2ms (cold)
               + Bytes::from_owner (zero-copy body)
CAS hashing    BLAKE3 (10x faster SHA-256)   ~50us per MB
DB reads       SQLite WAL + 8 reader pool    ~50us per query
DB writes      Dedicated writer connection    ~200us per write
Artifact GC    CAS ref-count + hardlinks      Background, hourly
```

**Key decisions:**
- SQLite WAL over Postgres (zero infra, unlimited concurrent reads, sufficient for single-VPS)
- In-memory broadcast over Redis (1000x faster, add Redis later behind EventBus trait if multi-server)
- mmap over sendfile (HTTP/2 + TLS invalidate kernel zero-copy)
- BLAKE3 over SHA-256 (same security, 10x throughput)
