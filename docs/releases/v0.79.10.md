> *Silent failures are not features. They are bugs with good manners.*

Every Nika release before this one quietly accepted three kinds of workflows that couldn't actually run. This release makes them fail at `nika check` instead — with structured errors, actionable fixes, and a supported-provider matrix.

---

## TL;DR

1. **`nika check` now fails fast on three capability mismatches** that used to silently succeed:
   - `extended_thinking: true` on any provider other than Anthropic
   - `stop_sequences: [...]` on rig-core providers (Mistral, Groq, DeepSeek, xAI)
   - `tool_choice: required` on rig-core providers
2. **New error: `NIKA-120 UnsupportedProviderCapability`** in the Resilience error range. Structured, typed, actionable — includes the supported-provider list for each capability.
3. **`ProviderCapabilities` is the single source of truth** — `nika-core::catalogs::providers` owns the capability matrix; `nika check`, agent loop, runtime, and `nika provider list` all consult it.
4. **`nika eval` migrates to the `jsonschema` crate.** Fifteen JSON Schema keywords are now honored — `minimum`, `maximum`, `pattern`, `enum`, `multipleOf`, `uniqueItems`, `minItems`, `maxItems`, `minLength`, `maxLength`, `format`, `$ref`, `allOf`, `anyOf`, `oneOf`.
5. **Zero breaking changes for workflow YAML.** Zero API break for embedders. **Upgrade may surface NIKA-120 on workflows that used to pass** — those workflows were silently broken; fix or change provider.

## The three silent failures

### 1. `extended_thinking: true` on non-Anthropic providers

Anthropic's extended thinking mode returns a separate reasoning trace alongside the final answer. The API shape looks like:

```json
{
  "type": "thinking",
  "thinking": "Let me approach this step by step...",
  "signature": "..."
}
{
  "type": "text",
  "text": "The answer is 42."
}
```

Other providers don't support this. Some return a similar-looking reasoning mode (OpenAI's `o1-preview` has its own reasoning tokens), but the API shapes are incompatible and Nika doesn't translate between them.

**Before v0.79.10:** `extended_thinking: true` on Groq (no support) was silently dropped by the rig-core adapter. The request went out without the flag. The response came back without a thinking trace. The `nika run` output looked identical to a non-thinking task. Users saw no error, no warning, just a missing feature they'd asked for.

**After v0.79.10:**

```text
$ nika check reasoning.nika.yaml

[NIKA-120] Task "reason_step" requests capability `extended_thinking`
but provider `groq` does not support it.

  Supported providers for extended_thinking: anthropic

  help: Change the task provider to `anthropic`, or remove the
        `extended_thinking` field. See `nika provider list` for the
        full capability matrix.
```

Exit code 1. CI fails. You see the problem before it ships.

### 2. `stop_sequences` on rig-core providers

`stop_sequences: ["\n\n", "Human:"]` tells the provider to stop generating when it sees one of these tokens. Anthropic and OpenAI honor it. Rig-core's provider adapters for Mistral, Groq, DeepSeek, and xAI don't — the field is silently dropped by the rig-core layer before the HTTP request is built. Your generations continue past the stop sequences you requested.

**After v0.79.10**, same treatment: `nika check` catches it, you either change provider or remove the field.

### 3. `tool_choice: required` on rig-core providers

`tool_choice: required` forces the model to call exactly one tool per turn (no plain-text response). Anthropic and OpenAI support it. Rig-core providers treat it as `auto` — the model may respond with plain text, defeating the "force a tool call" pattern.

**After v0.79.10**: flagged at check time. `tool_choice: auto` (the default) works on all providers; only `required` is capability-gated.

## The capability matrix

Published in `nika-core::catalogs::providers::ProviderCapabilities`:

| Capability | Supported on | Silent-drop before v0.79.10? |
|---|---|---|
| `extended_thinking` | `anthropic` only | Yes — dropped on all other providers |
| `stop_sequences` | `anthropic`, `openai` | Yes — dropped by rig-core providers |
| `tool_choice: required` | `anthropic`, `openai` | Yes — no-op on rig-core providers |
| `tool_choice: auto` | all 14 LLM providers | No — was already honored |
| `tool_choice: none` | all 14 LLM providers | No — was already honored |
| `vision` (image content) | `anthropic`, `openai`, `mistral`, `groq`, `gemini`, `xai` | Yes — rejected with `NIKA-389` (no change this release) |
| `native structured output` | `openai`, `groq`, `deepseek`, `xai` | N/A — falls back to L0 tool injection |
| `response_format: json_schema` | `openai`, `groq`, `deepseek`, `xai` | N/A — same as above |

Run `nika provider list --capabilities` to see the live matrix.

### The `ProviderCapabilities` struct

Single source of truth, queryable from any crate that consumes `nika-core`:

```rust
pub struct ProviderCapabilities {
    pub extended_thinking: bool,
    pub stop_sequences: bool,
    pub tool_choice_required: bool,
    pub vision: bool,
    pub structured_output: StructuredOutputKind,
    pub max_context_tokens: u32,
    pub max_output_tokens: u32,
    pub supports_streaming: bool,
    pub supports_temperature: bool,
    pub supports_top_p: bool,
    pub default_temperature: Option<f32>,
    // ...
}

pub fn capabilities_for(provider: &str) -> Option<&'static ProviderCapabilities> {
    // lookup in the static catalog
}
```

Before v0.79.10, this information lived in three places that drifted:

- A match statement in `nika-engine::provider::selection::is_capable` (incomplete)
- Partial metadata on individual `Provider` entries in `nika-core::catalogs::providers` (out of sync with the engine match)
- A hard-coded list in `nika-engine::runtime::rig_agent_loop::tool_injection::supports_tool_choice_required` (disagreed with both)

The drift was real. Groq, for example, was listed as supporting `tool_choice: required` in one location but dropped in another — result: mixed behavior depending on which caller resolved capability.

After v0.79.10: one match statement, one struct, one call site. The check is now deterministic.

## `nika eval` — full JSON Schema via `jsonschema` crate

`nika eval` runs workflows against a dataset and validates outputs against a schema. Before v0.79.10 it used a home-grown validator that handled the obvious keywords and silently ignored the rest:

| Keyword | Before v0.79.10 | After v0.79.10 |
|---|---|---|
| `type` | honored | honored |
| `required` | honored | honored |
| `properties.<field>.type` | honored | honored |
| `minimum` / `maximum` | **ignored** | **honored** |
| `exclusiveMinimum` / `exclusiveMaximum` | ignored | honored |
| `pattern` (regex) | ignored | **honored** (ECMA-262 via `regex` crate) |
| `enum` | ignored | **honored** |
| `multipleOf` | ignored | honored |
| `minItems` / `maxItems` | ignored | honored |
| `uniqueItems` | ignored | honored |
| `minLength` / `maxLength` | ignored | honored |
| `format` (`email`, `uri`, `date-time`, `uuid`) | ignored | honored |
| `$ref` / `$defs` | ignored | honored |
| `allOf` / `anyOf` / `oneOf` | ignored | honored |
| `if` / `then` / `else` | ignored | honored |

If your evals depended on `minimum` validation (e.g., `"age": {"type": "number", "minimum": 0}` catching `{"age": -5}`) — they didn't. Now they do.

If your evals were "passing" because the unsupported keywords were silently skipped — they will start failing. Fix the test outputs, or update the schema to match the actual output shape.

### Example

```yaml
# eval-dataset.json
{
  "cases": [
    {"input": "alice@company.com", "expected": { "domain": "company.com" }},
    {"input": "bob@invalid",       "expected": "NIKA-error" }
  ]
}

# workflow.nika.yaml
tasks:
  - id: parse
    infer: "Extract the domain from: {{inputs.email}}"
    structured:
      schema:
        type: object
        properties:
          domain:
            type: string
            format: hostname
            pattern: "^[a-z0-9.-]+\\.[a-z]{2,}$"
        required: [domain]
```

```bash
$ nika eval workflow.nika.yaml --dataset eval-dataset.json

case "alice@company.com"  PASS  (domain: "company.com")
case "bob@invalid"        FAIL  pattern mismatch: 'invalid' does not match
                                ^[a-z0-9.-]+\.[a-z]{2,}$
```

Before v0.79.10: `pattern` was ignored, so `{"domain": "invalid"}` passed. Now: caught.

## Migration

### If `nika check` now fires NIKA-120 on existing workflows

The check correctly identified a silent bug. Two fixes:

**Option A — change the task's provider to a supported one:**

```yaml
# Before
tasks:
  - id: reason
    provider: groq
    infer:
      extended_thinking: true    # ← NIKA-120
      
# After
tasks:
  - id: reason
    provider: anthropic          # ← supported for extended_thinking
    infer:
      extended_thinking: true
```

**Option B — remove the unsupported capability:**

```yaml
# Before
tasks:
  - id: reason
    provider: groq
    infer:
      extended_thinking: true    # ← drop this
      stop_sequences: ["\n\n"]   # ← drop this

# After
tasks:
  - id: reason
    provider: groq
    infer:
      # no extended_thinking, no stop_sequences
      # (Groq doesn't support them; use provider-appropriate features)
```

Both are correct fixes. Option A preserves your intent. Option B accepts the existing provider's actual capabilities.

### If `nika eval` results regress

The stricter validator is finding real problems in your test data. Review the failing cases:

- If the expected output is correct and the schema is wrong: fix the schema (tighten `pattern`, add `minimum`, etc.)
- If the schema is correct and the expected output is wrong: fix the dataset
- If the schema has a keyword you thought was enforced: now it is — update expectations
