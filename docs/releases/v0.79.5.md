## TL;DR

1. **New crate: `nika-builtin`** at architectural layer L2. Extracted from `nika-engine` (−3,227 LOC in the engine).
2. **24+ builtin tools migrated** across five commits: core (5), data (19), introspection (3), HITL bridge (1 via a kernel trait), file I/O (5). 17 media-opt-in tools remain feature-gated in `nika-media`.
3. **`BuiltinRouter` kernel trait** — `nika-engine::runtime::executor::invoke` now routes `invoke:` verb calls through a kernel trait, not a concrete registry. Engine becomes ignorant of the tool catalog.
4. **Reliability fixes** from the 5-agent review swarm: `exec-runner` pipe deadlock (`kill_on_drop` + `tokio::try_join!`), `jq` output cap at 100k elements (OOM prevention), `complete.rs` schema validation, `create_dir_all` deferred after path validation, empty-markers rejection.
5. **Zero breaking changes.** Workflow YAML unchanged. Tool names unchanged. Tool outputs identical.

## Why extract `nika-builtin`

The engine had 63 builtin tools implemented across ~15 files in `nika-engine/src/runtime/builtin/`. They had full read access to engine internals: `RunContext`, `EventLog`, `SecurityContext`, `MediaContext`, the datastore — everything. This was convenient while the engine was evolving, but it created two problems:

- **Tool implementations were untestable in isolation.** Unit-testing `nika:jq` required constructing a full engine execution context. 
- **Any engine internal refactor broke tool implementations.** During the Constellation work, 11 tool files had to be touched every time `RunContext` changed shape.

The fix: move the tools to their own crate, define a `BuiltinRouter` kernel trait, and pass only what each tool needs through the trait. Engine constructs the router; tools consume a narrow surface.

Flow-control primitives. No I/O, no external services.

- `nika:log` — structured log emission
- `nika:emit` — custom event emission  
- `nika:assert` — test assertions
- `nika:complete` — agent completion signal (with `#[builtin_tool]` + schema validation)

### Introspection tools (3)

Read-only access to workflow metadata through the kernel trait.

- `nika:dag_info` — DAG topology
- `nika:task_status` — current task statuses
- `nika:threads` — agent thread tree

### HITL bridge (1)

`nika:prompt` — human-in-the-loop input tool. The only tool with an explicit kernel trait bridge (`HitlPrompt`) because it needs a terminal or HTTP backchannel to prompt the user. Implementation stays in `nika-engine` (concrete `HitlHandler`), but the trait lives in `nika-kernel`, so the tool crate doesn't depend on the engine.

```

```

These required the most hardening — Shield integration, permission-mode enforcement, path validation, blocklist respect. They depend on the `FsRead` + `FsWrite` kernel traits (from `nika-fs`), not on concrete filesystem implementations.

## The `BuiltinRouter` kernel trait

```rust
// nika-kernel/src/builtin.rs
#[async_trait]
pub trait BuiltinRouter: Send + Sync {
    async fn call(&self, invocation: BuiltinInvocation<'_>) -> Result<BuiltinResponse, BuiltinError>;
    fn known(&self) -> &[&str];
    fn supports(&self, tool: &str) -> bool;
}
```

`nika-builtin::DefaultBuiltinRouter` implements this trait. `nika-engine::runtime::executor::invoke::run` takes `&dyn BuiltinRouter` and dispatches through it. For testing, `nika-kernel-mock::MockBuiltinRouter` provides fixture-friendly stubs.

`BuiltinInvocation<'_>` is a small struct carrying:
- tool name
- parameters (`&serde_json::Value`)
- trust level (`TrustLevel`)
- security context (`&SecurityContext`)
- event emitter (`&dyn EventEmitter`)

Nothing else. Tools receive exactly what they need, and the engine's internal state stays invisible.

## Reliability fixes (from the 5-agent review swarm)

The migration included an 18-commit hardening pass addressing P0/P1/P2 findings. Four are user-visible as reliability improvements:

### P0 — `exec-runner` pipe buffer deadlock (`8ef810b9f`)

**Before.** `nika:exec` ran shell commands via `tokio::process::Command`. If stdout was large and stderr was also written to (or vice versa), the child could block on a full pipe buffer while the parent blocked waiting for the child to exit. Classic Unix pipe deadlock. Reproducible with a subprocess emitting >1 MB to both stdout and stderr.

**Fix.** Every subprocess spawn now sets `cmd.kill_on_drop(true)` (invariant #11), and output is drained concurrently via `tokio::try_join!` over stdout/stderr/wait futures (invariant #12). Added a 64 MiB fixture test that exercises the previously-deadlocking path.

### P0 — `jq` output cap (`1c850e632`)

**Before.** A poorly-written jq expression (`.[] * 1000000`) could produce a 10-million-element array in memory and OOM the daemon process.

**Fix.** 100,000-element cap on jq output. Exceeds the cap, the expression fails with `NIKA-045 TransformOutputTooLarge` instead of exhausting memory. The cap is configurable via workflow policy in `nika.toml`.

### P1 — `complete.rs` schema validation (`6e1e3fe06`)

**Before.** Agent `nika:complete` tool accepted `{}` as output even when the task's `completion.schema` required fields. The schema check was performed by the agent loop after tool return, not by the tool itself — if the tool didn't populate required fields, the agent loop surfaced a confusing validation error without task context.

**Fix.** `complete` now validates its payload against the task's completion schema before returning, surfacing a `NIKA-301 StructuredOutputValidation` error inside the tool with the task ID attached.

### P1 — `create_dir_all` deferred (`4d574dcc7`)

**Before.** `nika:write` called `fs::create_dir_all(path.parent())` unconditionally, before path validation. If the path was then rejected (outside workflow base dir, blocked by permission mode, etc.), the mkdir remained. Left empty directories on the filesystem, worst case polluted the user's project.

**Fix.** Path validation runs first. Directory creation happens only after the path is accepted. Rejected writes leave zero filesystem residue.

### P2 — Empty markers validation (same commit as above)

`nika:write` accepts an `overwrite:` marker field. Empty-string markers used to pass validation silently, causing downstream detection logic to misfire. Now rejected with `NIKA-215 InvalidMarker`.

## Migration (for embedders only)

If you embed the Nika engine and call builtin tools directly:

```rust
// Before v0.79.5 (still works in this release, deprecated)
use nika_engine::runtime::builtin::jq::JqTool;
let tool = JqTool::new();

// After v0.79.5 (recommended)
use nika_builtin::data::JqTool;
let tool = JqTool::new();

// Even better — use the router
use nika_kernel::builtin::BuiltinRouter;
use nika_builtin::DefaultBuiltinRouter;
let router: Box<dyn BuiltinRouter> = Box::new(DefaultBuiltinRouter::new());
```

The old `nika_engine::runtime::builtin::*` re-exports are deprecated in this release and removed in **v0.80.0**.
