## TL;DR

1. **The "Layer 1 rig Extractor" structured-output defense layer is gone from the docs.** It was referenced in seven files across three releases (v0.77.x – v0.79.6) but never implemented. The code had no `enable_extractor` reader, no `rig::Extractor` call, no runtime wiring.
2. **Structured output is a 4-layer defense.** L0 (provider-native tool injection) → L2 (post-response JSON extract + `jsonschema` validation) → L3 (retry with validation error echoed back) → L4 (LLM repair with `repair_model`). **This is what was already working — now the docs say so.**
3. **New CI gate: unwrap ratchet.** `scripts/count-unwraps.py` counts production `.unwrap()` + `.expect()` calls and fails if the count exceeds the baseline (89). Prevents regression of `NikaError` coverage.
4. **Zero user-visible behavior change.** Your workflows produce identical output. The 4 defense layers were all there the whole time.

## The phantom

For three releases, `SECURITY.md` and the structured-output docs described a five-layer defense:

> Structured output defense stack:
> - **L0** — Provider-native tool injection (Anthropic tool_use, OpenAI response_format, Gemini generationConfig)
> - **L1** — rig Extractor (future)
> - **L2** — Post-response JSON extraction + jsonschema validation
> - **L3** — Retry with validation error echoed back to the model
> - **L4** — LLM repair using repair_model

The "L1 — rig Extractor (future)" entry was a placeholder. The design was: use [`rig::extractor`](https://docs.rs/rig/latest/rig/extractor/index.html) to post-process the raw text response and project it through a typed extractor before JSON parsing, as a safety net between L0 and L2. Nobody ever wired it up.

Evidence that L1 was never real:

```bash
# Search the entire repository for enable_extractor reader or rig::Extractor call
rg 'enable_extractor' tools/ --type rust | grep -v test | grep -v '//'
# → 0 production hits (only a write-only config field that was never read)

rg 'rig::Extractor' tools/ --type rust | grep -v test | grep -v '//'
# → 0 hits

rg 'Layer 1: rig Extractor' tools/**/*.rs
# → 0 hits (only the docstring in nika-engine/src/runtime/structured_output.rs)
```

The `enable_extractor: true` JSON schema field was defined on the `Structured` task config, parsed, stored in the `AnalyzedAction`, and never read again. Seven files — including `SECURITY.md`, the structured output handler docstring, the runtime docs, the verb-infer docstring, and a course exercise — referenced the layer as if it existed.

### What this release does

Deletes the claim everywhere:

- `nika-engine/src/runtime/structured_output.rs` docstring — rewritten
- `nika-core` JSON schema — `enable_extractor` field removed
- `nika-event` event docs — L1 references dropped
- `nika-verb-infer` docstring — updated to 4-layer
- `nika-runtime` (in v0.79.6 this crate was nuked; historically it carried the phantom too) — N/A
- Course exercise (in v0.80.0 the whole course is nuked; historically it carried a quiz about L1) — N/A
- `SECURITY.md` — updated structured output section (see honest stack below)

### The honest stack (4 layers)

```
L0  TOOL INJECTION     Provider-native: Anthropic tool_use, OpenAI
                       response_format json_schema, Gemini
                       generationConfig.responseSchema, mock provider's
                       synthetic schema fulfillment. If the provider
                       honors it, output is structured before it leaves
                       the wire.                                    [wired]

L2  EXTRACT + VALIDATE Post-response, the task handler extracts the first
                       JSON object from the text (handles markdown fences,
                       bare JSON, bracketed content) and validates it
                       against the user's schema via the jsonschema
                       crate.                                       [wired]

L3  RETRY WITH FEEDBACK  On validation failure, retry the call up to
                       max_retries (default: 2). The retry prompt includes
                       the validation error verbatim so the model knows
                       what to fix.                                 [wired]

L4  LLM REPAIR         On final validation failure, hand the raw response
                       + the schema + the validation errors to repair_model
                       (a cheaper model — defaults to a Haiku-class model)
                       and ask it to fix the JSON. One attempt.     [wired]
```

4 layers. All wired. All tested. All working the whole time.

## Unwrap ratchet (Z15 phase a)

Nika follows a zero-unwrap policy in production hot paths — every `Result` is handled via `NikaError` with a proper error code. But the codebase accumulated some unwraps in older code and in places where the author assumed a fallible call couldn't actually fail (which it can, under load, under exotic OS configs, under fuzzed input).

The zero-unwrap target is aspirational. The ratchet is practical: **the count doesn't go up.**

```bash
# scripts/count-unwraps.py
# Counts production .unwrap() and .expect() calls in tools/**/src/**/*.rs
# Excludes: tests, examples, benches, feature-gated code

$ python3 scripts/count-unwraps.py
Production unwraps: 89 (59 .unwrap() + 30 .expect())
```

The CI job runs `scripts/count-unwraps.py --check` on every PR. If the count exceeds 89, CI fails. Target is to decrement the number over time, session by session, until we hit zero in hot paths.

Baseline as of v0.79.7: **89 production unwraps**.

### Decomposition

| Crate | Unwraps | Comment |
|---|---:|---|
| `nika-engine` | 42 | Biggest offender — long list, slated for S25+ cleanup |
| `nika-core` | 8 | Mostly `Regex::new(CONSTANT)` in static init |
| `nika-display` | 14 | Format-string expect calls; mostly `write!` |
| `nika-media` | 9 | `image::DynamicImage::to_rgba8` in known-safe paths |
| `nika-verb-*` | 5 total | Split across the four verb crates |
| Other | 11 | Small tail |

Each unwrap is categorized in `scripts/unwrap-inventory.md` with a justification: "infallible in practice (LazyLock init)", "upstream returns `Result<T, !>` effectively", "will migrate when crate hits its extraction session". Unjustified unwraps fail CI.

### Where the ratchet lives

```
scripts/count-unwraps.py          counter + --check flag
scripts/unwrap-inventory.md       per-call justification
.github/workflows/ci.yml:unwraps  CI job that runs count --check
```
