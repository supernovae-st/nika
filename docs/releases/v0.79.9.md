## `nika-runtime` — the crate that was always about to be used

Introduced in Constellation session **S13** (January 2026) as part of the "diamond extraction" plan. The vision: `nika-runtime` at layer L3 would own DAG scheduling, verb dispatch, and binding orchestration, replacing the monolithic runtime logic in `nika-engine`.

What actually happened: two stub functions, a `dispatch()` with `NotImplemented` arms for four of the five verbs, an empty `BuildingBlocks` type, and 11 sessions of "coming soon in the next session" documentation.

Every constellation progress table from S13 onward said some variant of *"nika-runtime skeleton, activation pending."* Activation never came. The verb-dispatch logic stayed where it was (in `nika-engine/src/runtime/executor/mod.rs`). The crate stayed in the workspace for two reasons: (1) removing it required approval from the architect agent, and (2) the commit message "nuke(runtime): delete skeleton crate" felt like admitting defeat.

This release makes the admission. The crate is gone. The workspace is cleaner.

## `NIKA-383 InjectionDetected` + `NIKA-385 MlModelMissing` — the phantoms

Designed in Session 10 (November 2025) as part of the "6-layer Shield + ML detection" security plan. L5 was supposed to be an ML classifier that detected prompt-injection patterns at runtime:

- `NIKA-383 InjectionDetected` — raised when the L5 classifier scored an input above the detection threshold.
- `NIKA-385 MlModelMissing` — raised when the binary was built without the `shield-ml` feature, but a workflow requested L5 classification.

Neither error code was ever constructed. The `shield-ml` feature flag existed in `tools/nika-engine/Cargo.toml` but compiled into exactly zero runtime behavior. `SECURITY.md` claimed a 6-layer stack (L0 through L5 + L6 audit), but code shipped with **L0, L2, L3, L4, L5 (non-ML canary-based validation only), L6** — five wired defense layers plus one audit layer.

### Why they were shipped as placeholders

The plan was to commission a lightweight classifier (a small DeBERTa-style model or a rules-based pattern-match using something like `deberta-v3-base-prompt-injection-v2`), integrate it via `candle` or `ort`, and gate it behind the `shield-ml` feature. Three things killed it:

1. **Model selection drift.** Every candidate model had accuracy / latency trade-offs that didn't hold up against real prompt injections observed in the wild. The best candidates were 400MB+ and added ~50ms per `infer:` call.
2. **Dependency weight.** Adding `candle` or `ort` to the binary doubled the install size. For a `nika run` CLI tool that invokes once and exits, the cost-to-benefit was poor.
3. **False-positive cost.** ML-based injection detection has a 2-5% FP rate on benign inputs. At the scale Nika will operate, this means 1-in-20 legitimate workflows would be blocked with `NIKA-383`. The user experience was prohibitive.

The honest decision: don't ship ML-based detection at all. Use the deterministic defenses that already work (spotlight fencing, canary tokens, capability restriction). Document what actually protects users.

This release removes the code-level placeholders:

```rust
// Deleted from nika-engine/src/error.rs
#[nika_code("NIKA-383")]
ShieldInjectionDetected { score: f32, pattern: String },

#[nika_code("NIKA-385")]
ShieldMlModelMissing { feature: String },
```

And the docstring references across `SECURITY.md`, `README.md`, `MANIFESTO.md`, `CLAUDE.md`, `AGENTS.md`. The structured output "L1 rig Extractor" phantom was cleaned separately in [v0.79.7](./v0.79.7.md); this release cleans the Shield L5-ML phantom.

`SECURITY.md` now documents the honest 5-layer stack (L0 Policy + L2 Spotlight + L3 Structured + L4 Capabilities + L5 Validation + L6 Audit), with a **"Features cut (not planned)"** section explaining why the ML layer was scrapped. The codes `NIKA-383` and `NIKA-385` are permanently retired — any future Shield work will use fresh codes in the 390-399 range.

## Dead `pub(crate)` re-exports in the resolve shim (`575f4e224`)

The v0.79.8 binding architecture migration moved resolve functions to `nika-core` and left a thin engine shim for wiring. The shim re-exported nine helper functions as `pub(crate)` that were no longer used:

```rust
// Before (in nika-engine/src/binding/resolve_shim.rs)
pub(crate) use nika_core::binding::resolve::{
    resolve_path, resolve_pipe, resolve_default_value,
    resolve_task_u32, resolve_task_bool, resolve_required_bool,
    resolve_retry, resolve_action_templates, resolve_template,
};
```

A grep across the engine showed six of those nine symbols had no in-engine callers. The callers were all in tests that also moved to `nika-core` in S24. The re-exports were vestigial.

Deleted six of the nine. Kept three (`resolve_template`, `resolve_action_templates`, `resolve_task_u32`) that `runner/mod.rs` still calls through the shim.
