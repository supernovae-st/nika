# Research Report: Production-Grade TypeScript HTTP Client SDK Best Practices (2025-2026)

## Summary

This report analyzes the concrete patterns used by Stripe, OpenAI, Anthropic, Cloudflare, and Vercel AI SDKs to identify best practices for building a production-grade TypeScript HTTP client SDK. All four major AI SDKs (OpenAI, Anthropic, Cloudflare) are generated by **Stainless** and share identical architectural foundations. The patterns are battle-tested at massive scale.

---

## 1. SDK Design Patterns 2025

### Namespace Grouping: The Universal Pattern

Every major SDK in 2025 uses **resource namespaces on the client instance**. This is the dominant pattern, no exceptions.

```typescript
// OpenAI
const openai = new OpenAI();
openai.chat.completions.create({ ... });
openai.files.list();
openai.models.retrieve('gpt-4o');

// Anthropic
const anthropic = new Anthropic();
anthropic.messages.create({ ... });
anthropic.models.list();

// Stripe
const stripe = new Stripe('sk_...');
stripe.customers.create({ ... });
stripe.paymentIntents.list({ limit: 10 });
```

**Implementation pattern** (from Anthropic source):

```typescript
export class Anthropic extends BaseAnthropic {
  completions: API.Completions = new API.Completions(this);
  messages: API.Messages = new API.Messages(this);
  models: API.Models = new API.Models(this);
  beta: API.Beta = new API.Beta(this);
}
```

Each resource class receives the client reference and delegates HTTP calls back to it. This gives:
- Discoverability via autocomplete (`client.` -> see all resources)
- Clean separation of concerns (each resource in its own file)
- Nested namespaces where natural (`client.chat.completions`)

**Builder pattern**: Not used by any major SDK for request construction. All use **flat parameter objects** with TypeScript discriminated unions for variants:

```typescript
// OpenAI: streaming vs non-streaming via overloads, NOT builders
interface ChatCompletionCreateParamsNonStreaming { stream?: false; ... }
interface ChatCompletionCreateParamsStreaming { stream: true; ... }
```

### Key Finding: Flat methods with Options last

Every SDK follows the `method(params, options?)` signature:

```typescript
// The universal pattern
client.resource.action(
  { /* typed params */ },
  { /* request options: timeout, signal, headers, maxRetries */ }
)
```

### Client Construction

All SDKs read config from environment by default, with explicit overrides:

```typescript
// OpenAI constructor pattern
constructor({
  baseURL = readEnv('OPENAI_BASE_URL'),
  apiKey = readEnv('OPENAI_API_KEY'),
  ...opts
}: ClientOptions = {}) { ... }
```

Notable: OpenAI now supports **async API key functions** for credential rotation:

```typescript
apiKey?: string | (() => Promise<string>) | undefined;
```

### `withOptions()` for Client Forking

OpenAI exposes `withOptions()` to create a new client with overridden settings without mutating the original:

```typescript
const client2 = client.withOptions({ timeout: 60000 });
```

## 2. Native Fetch vs Axios in SDKs

### Verdict: Native fetch has won. Zero dependencies is the standard.

| SDK | HTTP Client | Dependencies |
|-----|-------------|--------------|
| OpenAI | Native fetch | **0 runtime deps** |
| Anthropic | Native fetch | 1 dep (json-schema-to-ts) |
| Stripe | Native fetch (v22+, was node-fetch) | **0 runtime deps** |
| Cloudflare | **Still node-fetch** | 6 deps (node-fetch, abort-controller, etc.) |
| Vercel AI | Native fetch | 0 runtime deps (workspace deps only) |

**Cloudflare is the outlier** — still shipping node-fetch + abort-controller polyfills. This is considered legacy.

### Native fetch is sufficient for SSE

Both OpenAI and Anthropic handle SSE via `fetch` + `response.body` (ReadableStream). No EventSource needed. The pattern:

1. `fetch()` returns a `Response` with `body: ReadableStream`
2. Convert ReadableStream to async iterable
3. Decode lines -> decode SSE events -> yield parsed JSON

### Node.js fetch considerations (2025-2026)

- **keepalive**: Node.js 22+ supports `keepalive` in fetch. For Node 18-20, the default undici connection pooling handles this adequately.
- **Automatic decompression**: Node.js fetch (undici) handles `gzip`/`br` automatically since Node 18. Not an issue.
- **Streaming uploads**: Requires `{ duplex: 'half' }` in fetch options (OpenAI handles this explicitly).
- **Custom fetch injection**: All SDKs allow `fetch: customFetchFn` in constructor for testing and edge cases.

### The Shim Layer

OpenAI/Anthropic use an internal `shims` module that abstracts platform differences:

```typescript
// internal/shims.ts
export function getDefaultFetch(): Fetch { ... }
export function ReadableStreamToAsyncIterable<T>(stream: ReadableStream): AsyncIterable<T> { ... }
export function CancelReadableStream(stream: ReadableStream | null): Promise<void> { ... }
```

This allows the same SDK code to work in Node.js, Deno, Bun, Cloudflare Workers, and browsers.

## 3. SSE/Streaming Best Practices

### The Stainless Pattern (used by OpenAI + Anthropic)

Both SDKs use an identical `Stream<Item>` class. NOT EventSource. Key architecture:

```
fetch response.body (ReadableStream)
  -> ReadableStreamToAsyncIterable
    -> iterSSEChunks (find double-newline boundaries)
      -> LineDecoder (handle partial UTF-8, \r\n vs \n)
        -> SSEDecoder (parse event: / data: / id: lines)
          -> yield ServerSentEvent { event, data, raw }
            -> JSON.parse -> yield Item
```

**Critical implementation details:**

1. **No EventSource**: SSE is parsed manually from fetch ReadableStream. EventSource has too many limitations (GET-only, no custom headers, no POST body, no abort control).

2. **Consumed-once guard**: Stream tracks `consumed` boolean, throws if iterated twice with helpful message about `.tee()`.

3. **Abort on break**: If user `break`s from `for await`, the `finally` block calls `controller.abort()` to stop the HTTP stream.

4. **Error events**: SSE `event: error` is caught and converted to `APIError` throw.

5. **[DONE] sentinel**: OpenAI uses `data: [DONE]` to signal stream end (Anthropic uses `event: message_stop`).

6. **`.tee()` for dual consumption**: Splits stream into two independent iterables using shared promise queue.

7. **`.toReadableStream()` for forwarding**: Converts back to ReadableStream for server-to-client proxying.

### Anthropic's Higher-Level MessageStream

On top of the raw `Stream<MessageStreamEvent>`, Anthropic provides `MessageStream` with:

```typescript
interface MessageStreamEvents {
  connect: () => void;
  streamEvent: (event, snapshot) => void;  // raw events + accumulated snapshot
  text: (textDelta, textSnapshot) => void;  // just text deltas
  thinking: (thinkingDelta, thinkingSnapshot) => void;
  inputJson: (partialJson, jsonSnapshot) => void;  // partial JSON parsing!
  message: (message) => void;         // complete message
  finalMessage: (message) => void;    // after all processing
  error: (error) => void;
  end: () => void;
}
```

This is a significant DX improvement: users get both the raw stream AND accumulated snapshots, plus partial JSON parsing for tool use arguments.

### Backpressure

Neither SDK implements explicit backpressure. The pattern relies on:
- `for await` naturally applies backpressure (won't pull next chunk until current is processed)
- Underlying fetch ReadableStream has built-in flow control
- No intermediate buffering beyond line/SSE decoder state

### Reconnection

Neither OpenAI nor Anthropic SDKs implement automatic SSE reconnection. If the stream drops:
- The async iterator ends (or throws)
- The user's `for await` loop exits
- Reconnection is left to the application layer

This is intentional: LLM streams are not idempotent, so automatic reconnection would produce duplicate/inconsistent output.

## 4. Error Handling Patterns

### The Universal Error Hierarchy

All Stainless-generated SDKs use the same hierarchy:

```
SDKError (base, non-API errors)
  └── APIError (has status, headers, body, requestID)
        ├── BadRequestError (400)
        ├── AuthenticationError (401)
        ├── PermissionDeniedError (403)
        ├── NotFoundError (404)
        ├── ConflictError (409)
        ├── UnprocessableEntityError (422)
        ├── RateLimitError (429)
        └── InternalServerError (500+)
  └── APIConnectionError (network-level, no response)
        └── APIConnectionTimeoutError
  └── APIUserAbortError (user called abort)
```

**Critical design decisions:**

1. **All errors extend native `Error`**: Stack traces work. `instanceof` works. Error cause chaining works.

2. **Typed status codes**: Error classes use generic type params for exact HTTP status:
   ```typescript
   export class BadRequestError extends APIError<400, Headers> {}
   ```

3. **Headers on errors**: Every API error carries the response headers, enabling rate-limit inspection.

4. **`requestID` on errors**: Anthropic extracts `request-id` header, OpenAI extracts `x-request-id`. Essential for support debugging.

5. **Static factory**: `APIError.generate(status, error, message, headers)` dispatches to the right subclass.

### Retry Logic

```typescript
// What gets retried (OpenAI/Anthropic):
408 -> true  // Request Timeout
409 -> true  // Lock Timeout (Conflict)
429 -> true  // Rate Limit
500+ -> true // Server Error

// Server override:
'x-should-retry: true'  -> always retry
'x-should-retry: false' -> never retry
```

### Rate Limit Header Handling

```typescript
// Priority order for retry delay:
1. `retry-after-ms` header (milliseconds, non-standard but supported proactively)
2. `retry-after` header (seconds or HTTP-date, standard)
3. Exponential backoff with jitter (fallback)

// Backoff formula:
sleepSeconds = min(0.5 * 2^numRetries, 8.0)  // 0.5s, 1s, 2s, 4s, 8s cap
jitter = 1 - random() * 0.25                   // up to 25% reduction
finalMs = sleepSeconds * jitter * 1000
```

### Default retry count: 2 (OpenAI/Anthropic), configurable per-client and per-request.

## 5. TypeScript SDK Publishing Best Practices 2025

### The Consensus: Dual CJS/ESM with `type: "commonjs"`

| SDK | `type` | Format | Build Tool |
|-----|--------|--------|------------|
| OpenAI | `"commonjs"` | Dual .js + .mjs | `tsc-multi` |
| Anthropic | `"commonjs"` | Dual .js + .mjs | `tsc-multi` |
| Stripe | (none) | Dual cjs/ + esm/ | Custom |
| Cloudflare | `"commonjs"` | Dual .js + .mjs | `tsc-multi` |
| Vercel AI | (none) | Dual .js + .mjs | `unbuild` (rollup) |

**Key: Nobody is ESM-only in 2025.** Despite the ecosystem push, all major SDKs ship dual format for maximum compatibility.

### `tsc-multi` Configuration

The Stainless SDKs use `tsc-multi` to compile TypeScript once and emit both formats:

```json
{
  "targets": [
    { "extname": ".js", "module": "commonjs", "shareHelpers": "internal/tslib.js" },
    { "extname": ".mjs", "module": "esnext", "shareHelpers": "internal/tslib.mjs" }
  ],
  "projects": ["tsconfig.build.json"]
}
```

### Exports Map

The OpenAI/Anthropic pattern (minimal, effective):

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.js"
    },
    "./*.mjs": { "default": "./dist/*.mjs" },
    "./*.js": { "default": "./dist/*.js" },
    "./*": {
      "import": "./dist/*.mjs",
      "require": "./dist/*.js"
    }
  },
  "types": "dist/index.d.ts",
  "main": "dist/index.js"
}
```

This allows deep imports like `import { Stream } from 'openai/core/streaming'`.

Stripe's pattern is more complex with platform-specific entries (browser, bun, deno, worker, workerd).

### Separate Entrypoints

Vercel AI SDK uses separate entrypoints for different concerns:

```json
{
  ".": { ... },
  "./internal": { "types": "...", "import": "...", "require": "..." },
  "./test": { "types": "...", "import": "...", "require": "..." }
}
```

**For an SDK wrapping REST + SSE**: A `/streaming` entrypoint is NOT standard. OpenAI/Anthropic export Stream from the main entry. The streaming code is small enough that tree-shaking handles unused code elimination.

### tsconfig Settings

From OpenAI's tsconfig (the strictest reasonable config):

```json
{
  "target": "es2020",
  "lib": ["es2020"],
  "module": "commonjs",
  "moduleResolution": "node",
  "strict": true,
  "exactOptionalPropertyTypes": true,
  "noUncheckedIndexedAccess": true,
  "noImplicitOverride": true,
  "noPropertyAccessFromIndexSignature": true,
  "isolatedModules": true,
  "skipLibCheck": true
}
```

### `engines` and Node.js version

All SDKs target **Node.js >= 18** (where native fetch became stable).

## 6. Testing SDKs

### Stripe: Custom HTTP Server Mock

Stripe does NOT use MSW. They spin up real `http.createServer()` instances:

```typescript
export const getTestServerStripe = (
  clientOptions,
  handler: (req, res, nPreviousRequests) => ...,
  callback: (err, stripe, closeServer) => void
) => {
  const server = http.createServer((req, res) => {
    handler(req, res, nPreviousRequests);
  });
  server.listen(0, () => {
    const { port } = server.address();
    const stripe = new Stripe('sk_test_123', { host: 'localhost', port, protocol: 'http' });
    callback(null, stripe, () => server.close());
  });
};
```

Plus a `stripe-mock` external process (Go binary) for full API simulation.

### OpenAI: Unit tests with `buildRequest()` inspection

OpenAI tests the request construction layer without making HTTP calls:

```typescript
test('headers are set correctly', async () => {
  const client = new OpenAI({ baseURL: 'http://localhost:5000/', apiKey: 'test' });
  const { req } = await client.buildRequest({ path: '/foo', method: 'post' });
  expect(req.headers.get('authorization')).toEqual('Bearer test');
});
```

For integration tests, they use a custom `fetch` function injection:

```typescript
const client = new OpenAI({
  fetch: async (url, init) => {
    // Return mock Response
    return new Response(JSON.stringify({ id: 'test' }), { status: 200 });
  },
  apiKey: 'test',
});
```

### Testing Strategy Summary

| Layer | Technique |
|-------|-----------|
| Request building | `client.buildRequest()` + inspect headers/body |
| Response parsing | Inject custom `fetch` returning mock `Response` |
| Error handling | Inject `fetch` returning error status codes |
| Retry logic | Custom HTTP server with controlled failure sequences |
| Streaming/SSE | `Stream.fromReadableStream()` with synthetic ReadableStream |
| Pagination | Mock server returning paginated responses |
| Integration | Real HTTP server or external mock service |

**MSW is not used by any of the major SDKs.** The `fetch` injection pattern is simpler and more reliable for SDK testing.

## 7. Observability

### Logger Interface

All Stainless SDKs expose a configurable logger:

```typescript
type Logger = {
  error: (message: string, ...rest: unknown[]) => void;
  warn: (message: string, ...rest: unknown[]) => void;
  info: (message: string, ...rest: unknown[]) => void;
  debug: (message: string, ...rest: unknown[]) => void;
};

// Usage
const client = new OpenAI({
  logger: myCustomLogger,
  logLevel: 'debug',  // or via OPENAI_LOG env var
});
```

### What Gets Logged

At `info` level:
```
[log_abc123] POST https://api.openai.com/v1/chat/completions succeeded with status 200 in 1234ms
```

At `debug` level:
- Full request details (method, URL, headers with auth redacted)
- Response details (status, headers, duration)
- Retry decisions and delays
- Request IDs for correlation

### No Middleware/Hooks System

**None of the major SDKs expose a middleware or hooks system.** The extension points are:

1. **Custom `fetch`**: Replace the entire HTTP layer
2. **Custom `logger`**: Observe all requests/responses
3. **`defaultHeaders`/`defaultQuery`**: Add to every request
4. **Per-request `RequestOptions`**: Override anything per-call

This is deliberate: middleware adds complexity and makes behavior harder to reason about. The `fetch` injection point is powerful enough for any custom behavior (metrics, tracing, caching).

### Request ID Propagation

Both OpenAI and Anthropic make request IDs available on:
- Successful responses via `.withResponse()`: `{ data, response, request_id }`
- Error objects: `error.requestID`
- Stream objects: `stream.response.headers.get('request-id')`

## 8. Pagination and Async Iterators

### OpenAI: `AbstractPage` + `PagePromise`

The OpenAI SDK's pagination is the most elegant. A paginated list call returns a `PagePromise` that:

1. **Is a regular Promise** (resolves to a Page object with `.data`, `.hasNextPage()`, etc.)
2. **Is also AsyncIterable** (can be used directly in `for await`)

```typescript
// Manual page control
const page = await client.files.list({ limit: 10 });
console.log(page.data);
if (page.hasNextPage()) {
  const nextPage = await page.getNextPage();
}

// Auto-paginating iteration (the magic)
for await (const file of client.files.list()) {
  console.log(file.id);
  // Automatically fetches next pages as needed
}

// Page-level iteration
for await (const page of client.files.list().iterPages()) {
  console.log(page.data);
}
```

**Implementation**: `PagePromise` extends `APIPromise` (which extends `Promise`) and implements `AsyncIterable`. The `[Symbol.asyncIterator]` delegates to the resolved page's iterator.

### Stripe: `autoPagingToArray` + `autoPagingEach`

```typescript
// Collect all into array (with safety limit)
const customers = await stripe.customers.list().autoPagingToArray({ limit: 100 });

// Iterate with callback
await stripe.customers.list().autoPagingEach((customer) => {
  console.log(customer.id);
});

// Also supports async iterator
for await (const customer of stripe.customers.list()) {
  console.log(customer.id);
}
```

### Key Design Pattern

```typescript
// The PagePromise is both a Promise AND an AsyncIterable:
class PagePromise<Page, Item> extends APIPromise<Page> implements AsyncIterable<Item> {
  async *[Symbol.asyncIterator](): AsyncGenerator<Item> {
    const page = await this;
    for await (const item of page) {
      yield item;
    }
  }
}
```

This dual nature means `const page = await client.list()` and `for await (const item of client.list())` both work naturally.

## 9. AbortController/Timeout Patterns

### Per-Request Signal

All SDKs support `signal` in request options:

```typescript
const controller = new AbortController();
setTimeout(() => controller.abort(), 5000);

const response = await client.chat.completions.create(
  { model: 'gpt-4o', messages: [...] },
  { signal: controller.signal }
);
```

### Client-Level Timeout

```typescript
const client = new OpenAI({
  timeout: 60_000,  // 60 seconds, default is 600_000 (10 minutes!)
});

// Per-request override
await client.chat.completions.create(params, { timeout: 30_000 });
```

### Implementation: `fetchWithTimeout`

The OpenAI pattern creates a dedicated `AbortController` per request:

```typescript
async fetchWithTimeout(url, init, ms, controller) {
  const abort = () => controller.abort();
  if (init.signal) init.signal.addEventListener('abort', abort, { once: true });

  const timeout = setTimeout(abort, ms);
  try {
    return await fetch(url, { ...init, signal: controller.signal });
  } finally {
    clearTimeout(timeout);
  }
}
```

Key: the user's `signal` and the timeout share the same `AbortController`. Either the user's abort or the timeout triggers cancellation.

### Streaming Abort

For streams, the `Stream` class exposes its controller:

```typescript
const stream = await client.chat.completions.create({ stream: true, ... });
// User can abort mid-stream:
stream.controller.abort();

// Or: breaking from for-await triggers abort automatically
for await (const chunk of stream) {
  if (shouldStop) break;  // triggers controller.abort() in finally
}
```

### Default Timeout: 10 minutes

All Stainless SDKs default to 600,000ms (10 minutes). This is intentionally high for LLM calls that can take minutes.

## 10. SDK Versioning and Backwards Compatibility

### Stainless-Generated SDKs: Spec-Driven Versioning

OpenAI, Anthropic, and Cloudflare SDKs are generated from OpenAPI specs. Their versioning:

- SDK major version tracks **breaking changes in the SDK interface** (not the API)
- API versioning is handled via headers (`anthropic-version`, `openai-beta`, etc.)
- SDK can support multiple API versions simultaneously

### Stripe: API Version Pinning

Stripe's approach is the gold standard for evolving APIs:

```typescript
const stripe = new Stripe('sk_...', {
  apiVersion: '2024-12-18.acacia',  // pin to specific API version
});
```

The SDK ships types for the latest API version but respects the pinned version for actual requests.

### Best Practices

1. **SemVer the SDK interface**: Major for breaking SDK changes, minor for new features, patch for fixes.
2. **API version as a parameter**: Let users pin their API version independently of the SDK version.
3. **Deprecation via TypeScript**: Mark deprecated params with `@deprecated` JSDoc — appears in IDE.
4. **Non-breaking additions**: New optional params, new response fields, new error types = minor version.
5. **Header-based versioning**: Use a header like `X-API-Version: 2025-01` rather than URL path versioning.
6. **Changelog automation**: Stainless auto-generates changelogs from OpenAPI spec diffs.

### The `withOptions()` Escape Hatch

```typescript
// User can override anything without forking:
const customClient = client.withOptions({
  baseURL: 'https://my-proxy.com/v1',
  defaultHeaders: { 'X-Custom': 'value' },
});
```

## Actionable Recommendations for a 7.6KB Zero-Dep SDK

Based on this research, here are prioritized recommendations:

### Must Have (P0)

1. **Error class hierarchy**: `SDKError > APIError > {RateLimitError, AuthenticationError, ...}` with `status`, `headers`, `requestID`.

2. **Retry with backoff**: 2 retries default, exponential backoff (0.5s base, 8s cap, 25% jitter), respect `Retry-After` header.

3. **`signal` + `timeout` support**: AbortController composition pattern from OpenAI. Default 10 min timeout.

4. **SSE via fetch + ReadableStream**: NOT EventSource. Manual line/SSE decoding. `Stream<T>` class implementing `AsyncIterable<T>`.

5. **Dual CJS/ESM build**: `type: "commonjs"`, emit `.js` + `.mjs` via `tsc-multi`. Wildcard exports map.

### Should Have (P1)

6. **Resource namespaces**: `client.jobs.submit()` not `client.submitJob()`. Each resource is a class that holds a client reference.

7. **`APIPromise` wrapper**: Extends `Promise` but adds `.asResponse()`, `.withResponse()` for accessing raw Response + request ID.

8. **Configurable logger**: Accept `{ debug, info, warn, error }` interface + `logLevel`. Log request/response at appropriate levels.

9. **Custom `fetch` injection**: For testing and edge runtime compatibility.

10. **`.tee()` and `.toReadableStream()` on Stream**: For SSE forwarding and dual consumption.

### Nice to Have (P2)

11. **`withOptions()` client forking**: Create variant clients without mutation.

12. **`dangerouslyAllowBrowser`**: Browser safety check (prevent accidental API key exposure).

13. **Pagination via `AsyncIterable`**: If the API has paginated endpoints, use the `PagePromise` dual-nature pattern.

14. **Platform detection headers**: Send `User-Agent` / `X-Stainless-Runtime` with SDK version, Node version, OS.

### Avoid

- **Axios**: Dead weight. Native fetch does everything needed.
- **EventSource**: Too limited for SDK use (GET-only, no headers, no abort).
- **Middleware/hooks system**: Over-engineering. `fetch` injection is sufficient.
- **ESM-only**: Breaks too many consumers in 2025. Ship dual.
- **MSW for testing**: Overkill. Custom fetch injection is simpler and more reliable.

## Further Research Suggestions

- **Stainless SDK generator**: The open-source `stainless-api/stl-api` tool could auto-generate the SDK from an OpenAPI spec, eliminating most manual work.
- **Zod integration**: Both OpenAI and Anthropic list Zod as a peer dependency for structured output parsing. Worth investigating for response validation.
- **React Native / Expo**: Both SDKs explicitly detect React Native and warn about missing streaming support. If RN is a target, `expo/fetch` is required.
- **WebSocket SDKs**: OpenAI's Realtime API uses WebSocket, not SSE. Different patterns needed if bidirectional communication is planned.
- **Rate limit proactive headers**: Some APIs send `X-RateLimit-Remaining`, `X-RateLimit-Reset` on every response. SDKs could expose these for client-side throttling.
